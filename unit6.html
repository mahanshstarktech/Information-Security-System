01

Symmetric Key Distribution

80% · Part B/C

The Problem — Why is Key Distribution Hard?

Symmetric encryption (DES, AES) requires both sender and receiver to share the SAME secret key. But how do they securely exchange that key in the first place, without an attacker intercepting it?

Imagine two people who want to pass secret notes in class. They first need to secretly agree on a code — but how do they agree on the code without the teacher (attacker) hearing? That's the key distribution problem.

If 1000 people want to communicate securely with each other, we'd need n(n-1)/2 = ~500,000 secret keys! This is clearly unscalable — and delivering each key securely is itself a problem. This is called the key distribution problem.

Solutions for Symmetric Key Distribution

1. Direct Physical Delivery (Courier)

The key is delivered physically — on a secure courier, USB drive, or in person. Secure but impractical for large-scale or online communication.

Example: Military organizations exchange codebooks physically before deployment.

2. Key Distribution Center (KDC) — Most Important!

A trusted third party called the KDC knows a long-term secret key for each user. When two users A and B want to communicate, they don't directly exchange keys. Instead:

KDC Session Key Distribution (Needham-Schroeder Protocol)
1. A → KDC: "I want to talk to B" + request ID
2. KDC → A: {Session key KS, Ticket for B}encrypted with A's master key
Ticket = {Session key KS, A's identity}encrypted with B's master key
3. A → B: Forwards the Ticket (B decrypts with B's master key to get KS)
4. A and B now communicate using Session key KS
KDC only needs to store n master keys for n users. Session keys are temporary.
Fig 1.1 — KDC Architecture: Central trust authority distributes session keys

3. Using Asymmetric Encryption (Hybrid Approach)

User A encrypts the symmetric session key with B's public key. Only B can decrypt with B's private key. This solves the key distribution problem without a KDC!

A generates random symmetric key KS
A sends B: E(PUb, KS) ← encrypted with B's public key
B decrypts: KS = D(PRb, E(PUb, KS))
Now A and B share KS and use symmetric encryption
This is exactly how HTTPS/TLS works — RSA or DH to exchange symmetric key, then AES for data
🔗
Connection — Unit 4 (RSA) + Unit 3 (AES) + Unit 6

Key distribution ties Units 4, 3, and 6 together! Unit 4 (RSA/DH) provides the mechanism to exchange keys securely. Unit 3 (AES/DES) is the symmetric cipher used once the key is shared. Unit 6 (SSL) = the real-world protocol that uses RSA key exchange + AES data encryption. This is called hybrid encryption — the most common pattern in real security systems.

Symmetric Key Distribution — Definition:
Symmetric key distribution is the process of securely delivering a shared secret key to two or more parties who wish to communicate using symmetric encryption. The challenge is: how do you securely share the key without an eavesdropper intercepting it?

The Problem:
If n parties need to communicate, n(n-1)/2 keys are needed. For 1000 users = ~500,000 keys. Managing and securely delivering this many keys is impractical — this is the key distribution problem.

Method 1: Using Symmetric Encryption (KDC Approach):
A trusted Key Distribution Center (KDC) maintains a long-term secret key with each user (Ka with user A, Kb with user B, etc.).
Steps:
1. A sends request to KDC: "I want session key to talk to B"
2. KDC generates session key KS and sends to A: E(Ka, [KS || E(Kb, [KS || ID_A])])
3. A decrypts to get KS and the Ticket (encrypted with Kb)
4. A forwards Ticket to B
5. B decrypts Ticket with Kb to get KS
6. Both A and B now use KS for further communication
[Draw KDC diagram as shown above]

Method 2: Using Asymmetric Encryption:
1. A generates a random session key KS
2. A encrypts KS with B's public key: C = E(PUb, KS)
3. A sends C to B
4. B decrypts: KS = D(PRb, C)
5. Both now share KS for symmetric encryption
Advantage: No KDC needed. Only B's public key is required (publicly available).
Disadvantage: RSA/public key encryption is slow — so only use it to exchange the symmetric key, not for actual data.

Concept of Public Key Infrastructure:
PKI manages the public keys through Certificate Authorities (CAs) that issue X.509 digital certificates binding identities to public keys. This ensures you're using the correct public key and not an attacker's fake key.

Distribution of Public Keys

🔥 85% — Very Important

Why is Public Key Distribution a Problem?

In asymmetric cryptography, public keys are supposed to be public — anyone can have them. But how do you know the key you received is really from the person you think it is? What if an attacker gives you their own fake public key while pretending to be your bank?

Imagine you want to send a secret letter to your bank using their "lock" (public key). But someone intercepts the delivery and substitutes THEIR own lock. You'd encrypt the letter with the attacker's lock — and they can open it! This is the man-in-the-middle attack on public key distribution.

4 Methods of Public Key Distribution

1. Public Announcement

User broadcasts their public key to everyone or posts it on a website/email signature. Simple but insecure — anyone can forge a public announcement claiming to be someone else.

2. Publicly Available Directory

Trusted public directory maintains {name, public key} pairs. Users register their public key with the directory authority. More trustworthy, but the directory itself can be attacked/compromised.

3. Public Key Authority

A central authority is responsible for distributing public keys on demand. When A wants B's public key, A requests it from the authority. The authority's response is signed with its own private key — A verifies with the authority's public key.

4. Public Key Certificates (Best Solution!)

A Certificate Authority (CA) issues digital certificates that bind a public key to an identity. The certificate is signed by the CA using the CA's private key. Anyone can verify the certificate using the CA's public key.

Certificate Structure (simplified)
Certificate = {Subject Name, Subject Public Key, CA Name, Validity Period, Serial No.}
Signed with CA's private key: Cert_signed = E(CA_private, Hash(Certificate))
Verification: Anyone can compute Hash(Certificate) and compare with D(CA_public, Cert_signed)

Public Key Distribution using Certificates:

The certificate approach solves the man-in-the-middle problem in public key distribution. A trusted Certificate Authority (CA) issues certificates — digitally signed documents that bind a public key to an identity.

Certificate Structure:
A public key certificate contains:
• Subject's name (e.g., "www.sbi.co.in")
• Subject's public key
• CA's name (issuer)
• Validity period (not before, not after)
• Serial number
• CA's digital signature on the above fields

How Certificate Distribution Works:
1. User A registers with CA: submits identity + public key
2. CA verifies A's identity (offline verification)
3. CA creates certificate: CA_Cert_A = Sign(CA_private, {A's identity + A's public key + validity})
4. A can now freely distribute CA_Cert_A to anyone
5. When B receives A's certificate, B verifies: Verify(CA_public, CA_Cert_A) → extracts A's trusted public key

[Draw: A → CA (registration) → A (certificate) → B (certificate) → CA (verify)]

Advantage over other methods:
No need to contact the CA at the time of verification — the certificate can be verified offline using the CA's widely-distributed public key. This makes it scalable and efficient (used in HTTPS on all websites).

X.509 Certificates

82% · Part B/C

What is X.509?

X.509 is an ITU-T standard that defines the format of public key certificates. It's the most widely used certificate format in the world — every HTTPS website uses X.509 certificates.

X.509 is like a standardized passport format. Just like all countries agree on what a passport must contain (photo, name, nationality, expiry), X.509 defines exactly what fields a digital certificate must have so that all computers can read and verify them the same way.

X.509 Certificate Format — Must Know for Exams

X.509 v3 Certificate Fields
Version : Version number (v1=0, v2=1, v3=2)
Serial Number : Unique identifier assigned by CA
Signature Algorithm: Algorithm used to sign the cert (e.g., SHA256withRSA)
Issuer : CA's Distinguished Name (who issued the cert)
Validity Period : Not Before + Not After (expiry dates)
Subject : Owner's Distinguished Name (who the cert is for)
Subject Public Key : The actual public key + algorithm
Extensions (v3) : Additional info — key usage, subject alt name
Signature : CA's digital signature over all above fields
Notation: CA<<A>> = certificate for user A issued by CA
Fig 3.1 — X.509 Certificate Chain: Trust flows from Root CA down to end-entity

Certificate Revocation

What if a certificate needs to be cancelled before expiry (private key compromised, employee left)? The CA publishes a Certificate Revocation List (CRL) — a list of revoked certificate serial numbers. Before trusting a certificate, always check the CRL or use OCSP (Online Certificate Status Protocol).

💡
X.509 Memory Trick — "VSS AVS-E"

Version, Serial, Signature Algorithm, Authority (Issuer), Validity, Subject, (public) Key, Extensions, Signature. Just remember: "Very Secure Systems Always Verify Subject Keys Every Signature." Write these 9 fields in a table format in exams — it fills space and shows depth.

Public Key Infrastructure (PKI)

82% · Part B/C

What is PKI?

Public Key Infrastructure (PKI) is a comprehensive system of policies, procedures, hardware, software, and standards needed to create, manage, distribute, use, store, and revoke digital certificates. It's the backbone of trusted internet communication.

PKI is like the entire passport system of a country — not just the passport itself (certificate), but also the passport office (CA), the rules for issuing passports (policies), how to verify them at border control (certificate verification), and how to revoke cancelled passports (CRL). Without the system around it, a single passport is just a piece of paper.

Components of PKI

  • Certification Authority (CA): Issues, signs, and manages certificates. The most trusted entity in the system. Example: DigiCert, Let's Encrypt, VeriSign. Root CA's certificate is self-signed and pre-installed in browsers.
  • Registration Authority (RA): Acts as intermediary between users and CA. Verifies user identity before CA issues certificate. Offloads CA's workload.
  • Certificate Repository: Public database where certificates and CRLs are stored. Usually LDAP directory. Anyone can download certificates from here.
  • Certificate Revocation System: CRL (Certificate Revocation List) or OCSP to invalidate compromised certificates.
  • Certificate Policy (CP) & Certification Practice Statement (CPS): Documents describing how the CA operates and what the certificate guarantees.

The public-key certificate technique is a solution to the problem of authenticating public keys — ensuring that a received public key genuinely belongs to the claimed entity and has not been tampered with.

Core Idea:
A trusted Certificate Authority (CA) creates a digital certificate that binds together: (1) the user's identity and (2) the user's public key, then digitally signs this binding with the CA's own private key.

X.509 Certificate Fields:
[List all 9 fields as described in Section 03 above — Version, Serial, Sig Algorithm, Issuer, Validity, Subject, Public Key, Extensions, CA Signature]

Certificate Creation Process:
1. User A generates a key pair (public key PUa, private key PRa)
2. A submits identity + PUa to Registration Authority (RA)
3. RA verifies A's identity (physical/online verification)
4. CA creates certificate: fields = {Version, Serial, A's name, A's PUa, CA name, validity, ...}

6. CA issues certificate to A

Certificate Verification:
When B receives A's certificate:
1. Extract CA signature from certificate
2. Compute Hash(certificate_fields)
3. Decrypt signature: H' = D(CA_public_key, CA_signature)
4. If H = H' → certificate is valid and untampered
5. Check validity period — not expired?
6. Check CRL — not revoked?
7. Extract A's public key → now B can trust PUa

PKI Components:
CA, RA, Certificate Repository, CRL/OCSP, Certificate Policy

• Scalable — certificates can be verified without contacting the CA each time
• Decentralized — works across the entire internet (HTTPS uses this for every website)
• Non-repudiation — CA's signature proves authenticity

Kerberos Authentication

🔥 90% — Very Important

What is Kerberos?

Kerberos is a network authentication protocol that uses symmetric key cryptography and a trusted third-party Authentication Server (AS) to authenticate users and services in a network. Designed by MIT's Project Athena, named after the three-headed dog guardian of Hades.

Kerberos is like a theme park ticketing system. When you arrive (login), you go to the ticket booth (Authentication Server) and show your ID. They give you a "master pass" (Ticket Granting Ticket). Whenever you want to ride an attraction (access a service), you show your master pass at the ride counter (Ticket Granting Server) to get a specific ride ticket. You show the ride ticket to the ride operator (service) to get in. The ride operator never needs to call the ticket booth — the tickets speak for themselves.

Kerberos Version 4 — Protocol Steps ⭐⭐⭐

Kerberos v4 involves three servers: Authentication Server (AS), Ticket Granting Server (TGS), and the Service Server (V).

Kerberos v4 — Complete Protocol (Memorize These 6 Steps!)
Step 1 — Authentication: C → AS: ID_C || ID_TGS || TS₁
Step 2 — AS Response: AS → C: E(Kc, [Kc,TGS || ID_TGS || TS₂ || Lifetime₂ || Ticket_TGS])
where Ticket_TGS = E(Ktgs, [Kc,TGS || ID_C || AD_C || ID_TGS || TS₂ || Lifetime₂])
Step 3 — TGS Request: C → TGS: ID_V || Ticket_TGS || Authenticator_C
where Authenticator_C = E(Kc,TGS, [ID_C || AD_C || TS₃])
Step 4 — TGS Response: TGS → C: E(Kc,TGS, [Kc,V || ID_V || TS₄ || Ticket_V])
where Ticket_V = E(Kv, [Kc,V || ID_C || AD_C || ID_V || TS₄ || Lifetime₄])
Step 5 — Service Request: C → V: Ticket_V || Authenticator_C2
Authenticator_C2 = E(Kc,V, [ID_C || AD_C || TS₅])
Step 6 — Service Response: V → C: E(Kc,V, [TS₅ + 1])
Kc = Key derived from user's password; TGS = Ticket Granting Server; TS = Timestamp; AD_C = Client address
Fig 5.1 — Kerberos v4: 6-step protocol for secure network authentication

Kerberos Phases Explained Simply

Phase 1: Authentication Service Exchange (Steps 1-2)

Client identifies itself to AS. AS returns a Ticket Granting Ticket (TGT) encrypted with the client's password-derived key Kc, and a session key Kc,TGS. The client decrypts using their password — if wrong password, decryption fails and authentication fails.

Phase 2: Ticket Granting Service Exchange (Steps 3-4)

Client presents TGT to TGS along with an Authenticator (proves client recently created this — prevents replay). TGS returns a Service Ticket encrypted with TGS-session key Kc,TGS.

Phase 3: Client/Server Authentication Exchange (Steps 5-6)

Client presents Service Ticket to target service. Service decrypts ticket, extracts service session key Kc,V. Step 6 is optional mutual authentication — service proves it can decrypt the authenticator.

Why Timestamps?

Tickets are time-limited (typically 8 hours). This prevents replay attacks — if an attacker captures a ticket, it will expire and become useless. Requires all clocks in the network to be synchronized (usually via NTP).

Kerberos Advantages & Limitations

AdvantagesLimitations
Single sign-on (SSO) — authenticate once, access multiple servicesSingle point of failure — if KDC goes down, no one can authenticate
Passwords never sent over network — only ticketsRequires synchronized clocks (within 5 minutes)
Replay attack protection via timestampsSusceptible to offline dictionary attacks on weak passwords
Mutual authentication — both client and server verifiedSession keys stored at KDC — compromise = all sessions exposed
Scalable within an organization (used in Windows Active Directory)Works within one realm — cross-realm authentication is complex
🧠
Kerberos Exam Trick — "3 Actors, 6 Messages"

Remember Kerberos with: 3 servers (AS, TGS, Service), 2 tickets (TGT and Service Ticket), 6 messages (①request AS, ②TGT+session key, ③request TGS, ④service ticket, ⑤present to service, ⑥confirmation). For diagrams: draw 4 vertical lifelines (Client, AS, TGS, Service) with 6 horizontal arrows. RTU awards 3-4 marks just for the correct diagram with arrow labels.

Kerberos Version 4 — Introduction:
Kerberos is a network authentication protocol developed at MIT that uses symmetric key cryptography and a trusted third party (Authentication Server) to authenticate users in a network. It provides single sign-on (SSO), meaning users authenticate once and access multiple services without re-entering passwords.

Terminology:
• C = Client (user), AS = Authentication Server, TGS = Ticket Granting Server, V = Service Server
• Kc = key derived from user's password, Ktgs = TGS's secret key, Kv = Service's secret key
• Kc,tgs = session key between C and TGS, Kc,v = session key between C and Service V
• TS = Timestamp, Lifetime = validity period of ticket

Protocol Steps:
Phase 1 — Authentication Service Exchange:
Step 1: C → AS: ID_C || ID_TGS || TS₁
(Client sends its ID and requests a TGT for TGS)
Step 2: AS → C: E(Kc, [Kc,TGS || ID_TGS || TS₂ || Lifetime₂ || Ticket_TGS])
where Ticket_TGS = E(Ktgs, [Kc,TGS || ID_C || AD_C || ID_TGS || TS₂ || Lifetime₂])
(AS returns session key + TGT, encrypted with client's password key)

Phase 2 — Ticket Granting Service Exchange:
Step 3: C → TGS: ID_V || Ticket_TGS || Authenticator_C
Authenticator_C = E(Kc,TGS, [ID_C || AD_C || TS₃])
(Client sends TGT + fresh Authenticator to prove identity to TGS)
Step 4: TGS → C: E(Kc,TGS, [Kc,V || ID_V || TS₄ || Ticket_V])
where Ticket_V = E(Kv, [Kc,V || ID_C || AD_C || ID_V || TS₄ || Lifetime₄])
(TGS returns service session key + service ticket)

Phase 3 — Client/Server Authentication Exchange:
Step 5: C → V: Ticket_V || E(Kc,V, [ID_C || AD_C || TS₅])
(Client presents service ticket to service)
Step 6 (optional): V → C: E(Kc,V, [TS₅ + 1])
(Service proves it decrypted correctly — mutual authentication)

Web Security Threats & Approaches

70% · Part A/B

Why is Web Security Important?

The web (HTTP) was designed for information sharing, not security. HTTP is plaintext — any data sent over HTTP can be read by anyone on the network. Web security threats exploit this and other vulnerabilities in web applications and protocols.

Sending data over HTTP is like sending a postcard — anyone who handles it (your ISP, network routers, hackers on public WiFi) can read it. Web security is about switching from postcards to sealed envelopes (HTTPS).

Four web security threats:

1. Eavesdropping: Attacker passively intercepts HTTP traffic on the network and reads sensitive data (passwords, credit card numbers) transmitted in plaintext.
2. Data Modification: Man-in-the-middle attacker intercepts and modifies data in transit — e.g., changing a bank account number in a payment.

4. Session Hijacking: Attacker steals a user's authenticated session cookie (via XSS or packet sniffing) to impersonate that user without knowing their password.

SSL Architecture & Protocol

🔥 95% — In Every Paper!
🔮 2026 Predicted — HIGH CONFIDENCE

What is SSL?

Secure Sockets Layer (SSL) is a cryptographic protocol developed by Netscape in 1994 that provides secure communication over a computer network. It has been succeeded by TLS (Transport Layer Security), but the term "SSL" is still colloquially used. SSL provides confidentiality, integrity, and authentication between a client (browser) and server (website).

SSL is the lock icon in your browser address bar. When you see "https://" and the padlock, that means SSL/TLS is active — your browser and the website are speaking in a secret code that no one else can understand. Your credit card number travels through this encrypted tunnel safely.

SSL Protocol Architecture — 4-Layer Stack ⭐⭐⭐

SSL sits between the Application layer (HTTP, FTP) and the Transport layer (TCP). It consists of two layers:

Fig 7.1 — SSL Protocol Stack: 4 sub-protocols at upper layer + Record Protocol at lower layer

The 4 SSL Sub-protocols (Upper Layer)

  • Handshake Protocol: Negotiates cipher suite, authenticates server (and optionally client), establishes session keys. The most complex sub-protocol — occurs ONCE per session.
  • Change Cipher Spec Protocol: Single byte message (0x01). Signals: "I'm switching from unencrypted to encrypted mode NOW!" Sent by both client and server during handshake.
  • Alert Protocol: Reports errors and warnings. Each alert has a level (warning or fatal) and a description code (e.g., bad_certificate, handshake_failure). Fatal alerts terminate the connection.
  • Application Data Protocol: Carries HTTP data (webpage content, form data) through the SSL Record layer.

SSL Record Protocol — Processing Steps ⭐⭐⭐

The SSL Record Protocol is the foundation — it carries all other protocols. It processes outgoing data through these 4 steps:

Fig 7.2 — SSL Record Protocol: 4 steps to process application data before sending
SSL Record Header Format
Content Type (1 byte): 20=ChangeCipherSpec, 21=Alert, 22=Handshake, 23=AppData
Version (2 bytes): Major.Minor (SSL 3.0 = 0x03 0x00; TLS 1.0 = 0x03 0x01)
Length (2 bytes): Length of the following compressed+MAC+padded data
Total header = 5 bytes. Maximum record size = 2^14 bytes (16,384 bytes)

SSL Handshake Protocol — Establishing a Session

The handshake negotiates all cryptographic parameters before data can be exchanged. Simplified flow:

1
ClientHello: Client sends SSL version, random number (client_random), list of supported cipher suites (e.g., TLS_RSA_WITH_AES_128_CBC_SHA256), compression methods.
2
ServerHello: Server selects best cipher suite from client's list, sends its own random number (server_random), session ID.
3
Certificate: Server sends its X.509 certificate. Client verifies it with CA's public key.
4
ServerHelloDone: Server indicates it's done with the negotiation phase.
5
ClientKeyExchange: Client generates a pre-master secret, encrypts it with server's public key (RSA), sends to server.
6
Both derive session keys: From pre-master secret + client_random + server_random → derive master_secret → derive 4 keys: client write key, server write key, client MAC key, server MAC key.
7
ChangeCipherSpec: Both sides signal "switching to encrypted mode now."
8
Finished: Both sides send a MAC of all handshake messages to verify the handshake was not tampered with. If MACs match, handshake is complete!
💡
SSL Cipher Suite Format — How to Read It

TLS_RSA_WITH_AES_128_CBC_SHA256 means:
• TLS = Protocol name
• RSA = Key exchange algorithm (how we exchange the symmetric key)
• AES_128_CBC = Bulk encryption (data encryption algorithm, key size, mode)
• SHA256 = MAC algorithm (for integrity)
RTU may ask you to interpret a cipher suite — use this breakdown format!

2023-Jul · Part B Q7 · 4 marks ⭐⭐SSL Record Protocol
SSL Record Protocol — Introduction:
The SSL Record Protocol is the lower sub-layer of SSL that provides the fundamental security services to all SSL protocols (Handshake, Alert, ChangeCipherSpec, and Application Data). It takes messages from the upper SSL sub-protocols, fragments them, optionally compresses them, applies a MAC for integrity, encrypts, and prepends an SSL record header.

Processing Steps (with diagram):
1. Fragment: Application data is fragmented into blocks of maximum 2^14 (16,384) bytes each.
2. Compress: Optionally compress the fragment (Note: TLS 1.3 removes this step as compression caused vulnerabilities like CRIME attack).
3. MAC (Message Authentication Code): Compute HMAC over the compressed data, sequence number, and other fields. Append MAC to the compressed fragment for integrity verification.
4. Encrypt: Encrypt the compressed data + MAC using the negotiated bulk cipher (AES in CBC mode, RC4 stream cipher). Then add the SSL Record Header.

SSL Record Header (5 bytes):
• Content Type (1 byte): 20=ChangeCipherSpec, 21=Alert, 22=Handshake, 23=ApplicationData
• Protocol Version (2 bytes)
• Length of payload (2 bytes)

[DRAW THE 4-STEP PIPELINE DIAGRAM: AppData → Fragment → Compress → +MAC → Encrypt → SSL Record]

SSL Record provides two services:
• Confidentiality: Payload is encrypted with shared symmetric key
• Message Integrity: MAC ensures payload hasn't been tampered with

SSL — Introduction:
SSL (Secure Sockets Layer) is a cryptographic protocol providing secure communication over the internet. Developed by Netscape in 1994; succeeded by TLS (Transport Layer Security) in 1999. It provides:
• Confidentiality (symmetric encryption of data)
• Authentication (X.509 certificate verification)
• Integrity (HMAC for each record)

SSL Architecture — 4-Layer Protocol Stack:
SSL sits between Application Layer (HTTP, FTP, SMTP) and Transport Layer (TCP).
Upper SSL Layer contains 4 sub-protocols:
[DRAW: 4 boxes: Handshake | ChangeCipherSpec | Alert | AppData — all above Record Protocol box]
Lower SSL Layer = Record Protocol (handles all data transmission)

1. SSL Handshake Protocol:
Most complex protocol. Establishes session by negotiating:
• Protocol version, Session ID
• Cipher suite (e.g., TLS_RSA_WITH_AES_128_CBC_SHA256)
• Compression method
• Authenticates server (and optionally client) via X.509 certificate
• Derives shared session keys from pre-master secret
[DRAW 8-step handshake: ClientHello → ServerHello → Certificate → ServerHelloDone → ClientKeyExchange → ChangeCipherSpec × 2 → Finished × 2]

2. Change Cipher Spec Protocol:
Simplest — single byte (0x01). Signals transition from pending cipher state to active. Both client and server send this message.

3. Alert Protocol:
Two fields: Level (warning=1 or fatal=2) + Description code
Fatal alerts immediately terminate the connection.
Examples: close_notify (normal closure), bad_certificate (cert verification failed), handshake_failure

4. SSL Record Protocol:
Fragments, compresses, adds MAC, encrypts, adds 5-byte header.
[DRAW the 4-step record processing pipeline]

Session vs Connection:
• SSL Session: Created by handshake, shared state between client and server (session ID, master secret, cipher suite). Can be used by multiple connections.
• SSL Connection: Transport link using session parameters. Short-lived, uses session's keys but different IVs/sequence numbers.

Applications: HTTPS (HTTP over SSL), FTPS, SMTP over SSL, online banking, e-commerce.

Transport Layer Security (TLS)

72% · Part A/B

TLS — The Successor to SSL

TLS (Transport Layer Security) is the standardized, improved version of SSL. Defined by IETF (Internet Engineering Task Force). Current version is TLS 1.3 (2018). All modern browsers use TLS 1.2 or TLS 1.3 — the name "SSL" still sticks colloquially.

TLS is like SSL 2.0 — a fixed, improved version released after security researchers found flaws in SSL. When your browser shows a lock icon, it's using TLS (not SSL), but everyone still calls it SSL. It's like how people say "Google it" but might be using Bing — the name stuck even after the thing changed.

TLS Improvements over SSL (for 4-mark answer)

  • HMAC instead of MAC: TLS uses HMAC (Hash-based MAC) which is stronger than SSL's MAC.
  • No export ciphers: TLS removed intentionally weakened "export grade" ciphers from SSL.
  • Better PRF: TLS uses a separate Pseudo-Random Function (PRF) based on HMAC for key material generation, instead of SSL's MD5+SHA1 combination.
  • Alert improvements: TLS adds new alert codes and clarifies existing ones.
  • Certificate verify: TLS changes how the certificate verify message is computed.

Q. In SSL and TLS, why is there a separate change cipher spec protocol rather than including a change-cipher-spec message in the handshake protocol?
2023-24 (61N0403) · Part B Q6 · 4 marksSSL/TLS
Reason for Separate ChangeCipherSpec Protocol:

The Change Cipher Spec (CCS) Protocol is intentionally separate from the Handshake Protocol for these reasons:

1. Clean state machine transition: SSL/TLS uses a state machine internally. The CCS message explicitly signals a clean transition between the "pending" cipher state (being negotiated) and the "current" (active) cipher state. Embedding this in the handshake would complicate the state machine significantly.

2. Ordering guarantee: CCS ensures that all handshake messages (including the Finished message that immediately follows) are processed in the correct order. The CCS acts as a barrier — everything before it uses old cipher parameters, everything after uses new parameters.

3. Flexibility: By separating CCS from the handshake, SSL/TLS allows for renegotiation — a new handshake can be initiated within an existing encrypted session, with CCS marking the transition point.

4. Error isolation: If the CCS message fails (e.g., network error), it's clearly identified as a cipher spec problem, separate from a handshake failure.

Note: TLS 1.3 effectively eliminated the CCS message as a functional component — it sends a dummy CCS for backward compatibility with TLS 1.2 middleboxes, but it has no actual effect in TLS 1.3.

HTTPS & SSH

HTTPS — HTTP over SSL/TLS

HTTPS (HTTP Secure) is HTTP running over SSL/TLS. It provides secure communication between a web browser and web server by encrypting all data exchanged. The default port is 443 (HTTP uses port 80).

HTTPS = HTTP + a security layer. Imagine HTTP is speaking in English in a crowded room — anyone can hear. HTTPS is speaking the same content but in a secret code that only you and the website know. Even if someone records your conversation (network traffic), they can't understand it.

SSH — Secure Shell

SSH (Secure Shell) is a cryptographic network protocol that allows secure remote login and other network services over an unsecured network. It replaces insecure protocols like Telnet (plaintext remote login), rlogin, rsh, and FTP. Default port: 22.

Before SSH, logging into a remote computer over the internet was like shouting your password across a crowded street — anyone could hear. SSH is like having a private secure phone call with the remote computer where everything is encrypted. Your password, commands, and responses — all private.

SSH Protocol Architecture — 3 Layers

  • Transport Layer Protocol: Provides server authentication, confidentiality, and integrity. Uses public key cryptography. Runs over TCP. Establishes an encrypted channel with the server.
  • User Authentication Protocol: Authenticates the client to the server. Methods: password, public key (SSH key pair), keyboard-interactive, GSSAPI/Kerberos.
  • Connection Protocol: Multiplexes the encrypted tunnel into multiple logical channels (terminal sessions, port forwarding, X11 forwarding, SFTP).
SSH Connection Flow
1. Client connects to server on port 22
2. Version exchange: both sides announce SSH protocol version
3. Algorithm negotiation: agree on encryption, MAC, key exchange algorithms
4. Key exchange (DH or ECDH): establish shared session key
5. Server authentication: server sends host key (public key); client verifies
6. User authentication: password or public key auth
7. Channel open: client requests terminal/shell; server grants access
SSH-2 (current) supports multiple simultaneous channels (SFTP, port forwarding) over one connection

SSH Key-based Authentication (No Password!)

The most secure SSH authentication method:

1
Generate key pair: ssh-keygen -t ed25519 → produces id_ed25519 (private) and id_ed25519.pub (public)
2
Copy public key to server: ssh-copy-id user@server → appends to ~/.ssh/authorized_keys
3
During login: server sends a challenge encrypted with client's public key. Only client's private key can decrypt it → proves identity without sending password!

Q. What is HTTPS? Why is HTTPS preferred over HTTP?
All Papers 2022–2025 · Part A Q10 · 2 marks ⭐⭐⭐ (Appears Every Year!)HTTPS
HTTPS (HyperText Transfer Protocol Secure) is HTTP running over the SSL/TLS protocol. It provides a secure, encrypted channel between a web browser and web server over port 443.

Why HTTPS is preferred over HTTP:
1. Confidentiality: HTTPS encrypts all data between browser and server (using AES/SSL). HTTP sends data in plaintext — anyone on the network can read it.
2. Authentication: HTTPS verifies the server's identity via X.509 digital certificate. HTTP has no server verification — you could be talking to a fake website (phishing).
3. Integrity: HTTPS uses HMAC to ensure data has not been modified in transit. HTTP has no protection against man-in-the-middle modification.
4. Trust indicator: Browsers show padlock icon for HTTPS — users trust it. Google also ranks HTTPS sites higher in search results.
